# 双轨审查与事实门禁

输入当前简历、事实侧录、`facts.yaml`、JD 和要求映射。可附实际拟上传文件。输出 [audit.yaml](assets/audit.template.yaml)。独立调用时使用实际文件名；没有 requirements 时先从 JD 建立带原文与事实 ID 的要求条目并保存，不能凭记忆评分。

## 审查顺序

1. 核对输入版本及内容。将侧录的每项 text 与正文核对，并反向检查正文是否有漏标的事实性陈述。ID 或版本相同不证明内容未变；发现改动就视为新版本。没有侧录可先补建，不能跳过追溯。将本次实际审查的事实、JD、要求映射、正文和侧录原样复制到 `audit-inputs/<报告版本>/`，在 snapshot_files 中逐个记录 live 与 snapshot 路径；有附件也保留该文件快照。不同版本不可覆盖旧快照，快照只留在用户本地运行目录。无写文件能力时返回这些完整文本供用户保存，未保存快照则只提供诊断，eligible_for 为 none。
2. **事实门禁：**每条陈述均须由有来源的 confirmed 事实支持；核对日期、数字、技能程度、个人职责、团队归属和因果关系。未解决的 humanize.fact_issues、错误引用、争议事实、未标注事实或版本不一致均阻塞。报告对应 claim_id、原句、理由和退回阶段。
3. **ATS 轨：**逐项列出 JD 要求及 `supported / partial / gap / unknown`，说明正文证据与实际能力缺口。关键词命中不等于满足要求，不能通过重复关键词提高结论。检查标准章节、阅读顺序和联系方式。能力缺口通常是提示，不替用户决定投不投。
4. **实际文件解析：**只有拿到当前拟上传文件并实际提取文本，才可判断其文字完整性和阅读顺序。记录文件版本、工具、观察结果；有权限时检查平台预览。只看 Markdown 或截图时 `unverified`。文件可读也不等于通过某家 ATS 或获得排名。
5. **表达轨：**定位空泛措辞、重复句式、夸张修饰和语域不符，分别给出原句、建议与理由。保留技术术语；不输出“AI 生成概率”，不把表达问题用 ATS 得分抵消。
6. 汇总 `blocking_issues` 和 `warnings`，不合成总分。`eligible_for` 取 `none / text_preparation / attachment_preparation`。事实未过、必需结构有实质错误或未解决的表达问题时为 none；文本通过但无文件验证为 text_preparation；当前附件实际解析通过且与已审正文一致才为 attachment_preparation。

## 退回与放行

- 事实缺失/冲突 → dig；事实已有但投影错误、无依据表述、正文结构或侧录遗漏 → tailor；只有表达问题 → humanize；附件解析失败 → 用户/宿主导出工具修复，再 audit。
- 已知联系方式缺失或 JD 能力缺口可作为 warning 允许文本准备，但申请表的必填缺项必须在 apply 中保留待处理。
- 版本不一致先重新审查当前输入。报告本身不编辑正文或事实；整改后产生新报告。正常文风偏好可作为 warning，必须修改的表达问题列为 blocking，不能含糊放行。
- `eligible_for` 只允许进入相应准备步骤，不代表用户已确认定稿，更不授权提交。任何正文、事实、JD、要求映射、侧录或附件变更都会使所依赖的报告失效。
