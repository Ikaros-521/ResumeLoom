# 简历表达改写

输入 `resume-draft.md`、`draft.meta.yaml`、`facts.yaml`，已有 `requirements.yaml` 时一并读取。输出 `resume-humanized.md`、`humanized.meta.yaml`。使用 [侧录模板](assets/humanized.template.yaml)。本 Skill 不改写事实档案。

独立调用未提供 JD 或 requirements 时，相应 inputs 填 null，不能照抄模板版本或虚构文件；只保留草稿中有来源且已核对的绑定。此模式可完成表达改写，但不检查 JD 覆盖，报告该限制。

## 执行

1. 先核对草稿事实侧录与当前正文逐句一致，输入档案版本一致。缺失侧录时可依据事实档案补建，但明确核对每项姓名、时间、技能和经历，不能默认为可信；无法核对则 `needs_facts`。
2. 采用简历语域：中立、具体、简洁。删除“深度赋能”“全方位助力”等空话，减少重复开头、堆叠形容词与冗长名词结构。不要为了人声添加第一人称、口语、情绪或刻意的不规则句式。原文已清楚时可不改。
3. 保留数字、日期、专名、技术关键词、限定条件、职责与成果归属。不得把“参与”改成“主导”、把团队成果改成个人成果、把“排查”改成“实现性能提升”。语句更自然不构成改事实的理由。
4. 如草稿本来就包含无依据的“主导”“提升40%”，列入 `fact_issues`，说明需要 dig 核实或 tailor 删除。可以输出排除问题陈述的修订候选，但状态保持 `needs_facts`，不能静默删除后声称事实已通过。
5. 保留已有 claim ID，按新正文更新 text；合并句子时合并其 fact_ids，拆句时使用新 ID 并记录关系。审查每一项事实陈述，包括未改的部分。`changes` 记录前后原句与改写理由。
6. 输出新版本与完整输入版本绑定；原草稿不覆盖。传递原有 open_questions，并补充本次问题。不得宣称改写能绕过 AI 检测或证明人类写作。

## 完成条件

可用事实含义不变，正文和侧录一致，技术术语保留；无事实问题时 `ready`，否则 `needs_facts` 并给出具体退回点。此状态只表示表达阶段完成，仍需独立 audit。
