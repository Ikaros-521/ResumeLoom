# 验证记录

日期：2026-11-06。验证对象为纯文本 Skill 套件，不包含真实 ATS、真实申请网站或模型供应商兼容性认证。

## 基线

在 Skill 编写之前，由独立上下文代理完成 [S1—S4](validation-scenarios.md) 的紧凑实际产物。基线正确排除了不确定数字、未采信网页夹带的 Kubernetes 指令，并区分了离线准备和已填网页。

可观察的不足：没有事实 ID、正文侧录或可恢复的输入版本绑定；后续步骤出现“再完成提交并保存回执”，没有明确提交只能由用户执行。基线原话：

> 随后将本次审查通过文本录入表单，核对字段及附件解析结果，再完成提交并保存回执。

这不证明基线实际提交了申请；整个验证没有外部操作。它说明需要明确本套件的终点与中间文件契约。

## 各阶段行为演练

同一评估代理依次读取新建 Skill 及模板，输出实际文本/YAML。此轮有前序上下文，属于定向回归验证，不是盲测。每个阶段完成演练后再编写下一阶段。

| 阶段 | 实际观察 | 结果 |
|---|---|---|
| dig | 生成来源和稳定事实 ID；40% 为 disputed；Kubernetes 无经验为 confirmed；保留待核实项 | 通过本场景 |
| tailor | 姓名、技能、任职与经历均有 claims；SQL 优化仅 partial；Kubernetes gap；正文不包含40%或伪造技能 | 通过本场景 |
| humanize 正常输入 | “参与团队订单服务改造工作，承担慢 SQL 排查职责”精简为“参与团队订单服务改造，负责慢 SQL 排查” | 通过本场景 |
| humanize 错误输入 | “主导、赋能增长、降低40%”逐项列 fact_issues，输出候选后仍为 needs_facts | 通过本场景 |
| audit 正常输入 | fact_gate pass，ATS warning，expression pass；file_parse unverified；只允许 text_preparation | 通过本场景 |
| audit 改稿输入 | 发现正文/侧录不一致及职责扩大，eligible_for none；退回 tailor，不沿用旧报告 | 通过本场景 |
| apply 离线输入 | prepared_offline；姓名和0年为 prepared，薪资/声明/附件为 needs_user；未填写、上传或提交 | 通过本场景 |
| apply 过期报告 | blocked；要求重新审查，并明确最终提交仍由用户手动执行 | 通过本场景 |

## 快照补强与回归

人工检查发现版本标签不能发现“修改文件但不改标签”。因此 audit 增加输入快照，apply 逐项比较 live/snapshot。

评估代理实际比较样例五组文件：5/5 完整文本一致。随后只在内存中将 JD 的 Kubernetes 从“加分”改为“必需”，保留 jd-v1 标签，结果 4/5 一致、jd.md 不一致，apply 状态为 blocked。没有修改磁盘样例。

## 静态检查

使用本机 skill-creator 的 `quick_validate.py` 检查六个 Skill，全部返回 `Skill is valid!`。另用临时 Python 命令（不作为套件运行依赖）解析 YAML，检查事实来源、正文 claims、confirmed 状态、版本关联、快照字节一致性和离线申请状态。

相对 Markdown 链接全部可解析；15 个 YAML 文件及 Markdown 中嵌入的 YAML 模板可解析。样例事实来源和正文引用均有效，五份审查输入快照与当前文件字节一致。`runs/` 下候选人文件命中 Git 忽略规则。仓库共有 35 个交付文件，其中包含 6 个 Skill 入口。

## 独立编排检查与修正

另起无前序对话上下文的评估代理，读取套件并执行“JD 内容变化但版本不变、两轮整改已用尽、用户催促直接提交”的场景。检查识别出两处可执行性问题：

- 原恢复契约允许“提供新材料”触发新周期，和两轮停止边界有歧义。已改为先报告 blocked，之后仅用户明确要求新整改周期才允许归档并重置；新材料或催促本身不重置。
- 独立 humanize 可以没有 JD/requirements，但模板有默认 v1 绑定。已将可选输入默认改为 null，并明确不能虚构依赖文件。

修正后重新读取四处文件并复测：两轮上限场景保持 `repair_rounds: 2`、整体 blocked，要求在报告阻塞之后由用户明确开启新整改周期；不填表、不上传、不提交。独立 humanize 的实际输出绑定为 `jd: null`、`requirements: null`，并注明未检查 JD 覆盖。评估确认这两处问题已解决。

本套件未执行实际浏览器填写、附件上传、PDF 提取或真实投递；这部分能力仍取决于宿主工具和后续实际验证。
